# ILI9341-TFT-TouchGFX — STM32F446RE + TouchGFX + FreeRTOS Reference Project

A working reference application for the 2.8" ILI9341 SPI TFT with XPT2046
resistive touch, built on an STM32F446RE (Nucleo-64), TouchGFX, and
FreeRTOS (CMSIS-RTOS2). The point of this repository is this project: a real,
buildable app that shows how to wire CubeMX-generated code, a hand-written
`App/` layer, and a CubeMX-decoupled `tft_drivers` driver library together
cleanly.

**Tested on:** STM32F446RE (Nucleo-64)
**GUI framework:** TouchGFX (project under `Profiles/board_1/TouchGFX/`)
**HAL:** STM32 HAL (CubeMX-generated), reached only through `App/drv_constants.h`

## Project layout

```text
ILI9341-TFT-TouchGFX/
├── CMakeLists.txt              # top-level glue — never regenerated by CubeMX
├── CMakePresets.json           # Debug / Release presets (Ninja + arm-none-eabi)
├── App/                        # hand-written application layer
│   ├── CMakeLists.txt          # drv_platform contract, tft_drivers, app sources
│   ├── drv_constants.h         # THE bridge: DRV_*/APP_* macros → CubeMX symbols
│   ├── app_main.c / .h         # App_Init() / App_CreateTasks(), called from main.c
│   ├── system.c / .h           # RTC/UART glue — the only other file touching raw handles
│   └── drivers/                # the tft_drivers library (see its own README)
│       ├── CMakeLists.txt      # tft_drivers static-library target (+ options)
│       ├── include/drv/, src/, adapters/, templates/, cmake/
│       ├── tests/              # host unit tests + hardware smoke checklist
│       └── datasheets/
└── Profiles/
    └── board_1/                # CubeMX + TouchGFX Designer output — never hand-edited
        ├── board_1.ioc
        ├── Core/ (Inc, Src)    # main.c, stm32f4xx_it.c, FreeRTOSConfig.h, ...
        ├── Drivers/ (CMSIS, STM32F4xx_HAL_Driver)
        ├── Middlewares/ (FreeRTOS, ST/touchgfx)
        ├── TouchGFX/           # Designer project, generated UI, target HAL glue
        ├── cmake/stm32cubemx/CMakeLists.txt
        ├── startup_stm32f446xx.s
        └── STM32F446XX_FLASH.ld
```

The UI itself is a TouchGFX Designer project under
`Profiles/board_1/TouchGFX/`: `gui/` holds the hand-written model/view/
presenter code, `generated/` the Designer output, and `target/` the board
glue that binds TouchGFX to `tft_drivers` — `TouchGFXDisplayDriver.cpp`
(flush → `ILI9341_FlushAsync`) and `STM32TouchController.cpp`
(`sampleTouch` → `XPT2046_ReadPoint`). `App/app_main.c` owns the TouchGFX
task and the ~60 Hz VSync timer that paces it.

**Rule:** nothing outside `Profiles/board_1/` is ever touched by CubeMX
regeneration, and the only lines added inside it live in `USER CODE` blocks —
`Core/Src/main.c` and `Core/Src/freertos.c` each need exactly one include and
one function call (`App_Init()` / `App_CreateTasks()`). See
[App/drivers/README.md](App/drivers/README.md#wiring-app_init--app_createtasks)
for the exact wiring.

The driver library itself — its architecture, the `drv_constants.h` and
`drv_platform` contracts, CMake options, interrupt wiring, the TouchGFX
integration notes, bare-metal usage, testing, and the full CubeMX peripheral
setup steps — is
documented in **[App/drivers/README.md](App/drivers/README.md)**. That
directory is a self-contained, CubeMX-free library that happens to live here;
drop it into `App/drivers/` of any other project the same way.

## Build

Presets target the STM32CubeCLT `arm-none-eabi-gcc` toolchain via
`Profiles/board_1/cmake/gcc-arm-none-eabi.cmake` (falls back to whatever
`arm-none-eabi-gcc` is on `PATH` if the CubeCLT install path isn't found).

```bash
cmake --preset Debug
cmake --build --preset Debug
```

```bash
cmake --preset Release
cmake --build --preset Release
```

Both presets pass `-DPROFILE=board_1` (the default). Flashing (from
`.vscode/tasks.json`):

```bash
STM32_Programmer_CLI -c port=SWD -w build/Debug/01_Display.elf -v -rst
```

## Debugging (Cortex-Debug Live Watch)

Two `volatile` globals expose driver state so you can watch it live — without
halting the core — from the **LIVE WATCH** panel of the bundled Cortex-Debug
launch configs (`.vscode/launch.json`):

| Global | Source | Fields |
| --- | --- | --- |
| `g_xpt2046_debug` | `App/drivers/src/xpt2046.c` | `raw_x/raw_y`, `px/py`, `pen_down`, `read_count`, `press_count` |
| `g_ili9341_debug` | `App/drivers/src/ili9341.c` | last flush `x/y/w/h`, `bytes`, `flush_count`, `done_count`, `busy` |

`g_xpt2046_debug` updates on every `XPT2046_ReadPoint()` (touch poll);
`g_ili9341_debug` updates on every `ILI9341_Flush()`/`ILI9341_FlushAsync()`
(frame block). Both survive optimization (they're `volatile` with external
linkage) and sit at fixed RAM addresses in Debug and Release builds. Add the
symbol name to Live Watch and it samples in the background.

## Setting the RTC from a browser (Web Serial)

The RTC is battery-backed (VBAT), so time survives power cycles — it just
needs to be set once. Open
[`dashboard/rtc-dashboard.html`](dashboard/rtc-dashboard.html) in Chrome or
Edge, click **Connect**, and pick the board's VCP (ST-LINK) port. The
dashboard shows the device clock live, and can set it manually or sync it
to the computer's clock (aligned to the next whole second).

The wire protocol runs over the existing USART2 @ 115200, ASCII lines:

```text
host → device                     device → host
SET 2026-07-19T14:30:22           OK SET 2026-07-19T14:30:22  (or ERR BADFMT/BADVAL/...)
TIME?                             TIME 2026-07-19T14:30:22
PING                              PONG rtc-clock 1.0
(unsolicited, 1 Hz)               RTC 2026-07-19T14:30:22
```

Implementation: `App/clock_protocol.c` (HAL-free parser/formatter,
host-tested), `App/system.c` (RTC set/get + interrupt-driven UART RX),
`time_sync_task` in `App/app_main.c`. A successful `SET` also stamps
`RTC_BKP_DR0`, so the first-boot seed in `MX_RTC_Init()` never overwrites a
host-set clock.

## Porting to a new board

1. `cp -r Profiles/board_1 Profiles/board_2` — or generate fresh from CubeMX
   into `Profiles/board_2/`.
2. Copy and edit `App/drv_constants.h` for the new pin/handle mapping.
3. Build with `-DPROFILE=board_2`.

No changes to `App/drivers/` (the library) are needed — board variation
lives entirely in `drv_constants.h` content. See
[App/drivers/README.md](App/drivers/README.md#porting-to-a-new-board) for
more detail.
